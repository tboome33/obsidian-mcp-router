## The bug

### Symptom

A user opens the Claude Code "Compétences" (Skills) panel for the `obsidian-router` plugin. The panel lists 32 entries. The first 14 (`autoresearch`, `canvas`, `defuddle`, `meta-*`, `obsidian-bases`, `obsidian-markdown`, `save`, `wiki*`) render correctly. The remaining 17 (`auto-mode`, `discover-list-files`, `discover-list-vaults`, `lock`, `manage-delete`, `manage-move`, `read-frontmatter`, `read-get`, `read-search`, `read-search-smart`, `template-execute`, `unlock`, `write-append`, `write-create-or-replace`, `write-patch`, `write-frontmatter-set`, `write-frontmatter-merge`) all produce the same error in the right pane:

```
Impossible de charger les fichiers de compétence.
Plugin not found: obsidian-router@obsidian-mcp-router-marketplace
```

### Root cause

The error wording is misleading. The plugin **is** correctly installed (`installed_plugins.json` shows `obsidian-router@obsidian-mcp-router-marketplace` at v0.8.6, install path resolves to a valid folder, all files present).

The actual cause: the panel iterates **both** the plugin's `skills/` directory AND its `commands/` directory, displaying everything as "compétences". When the user clicks an entry, the loader looks for `skills/<name>/SKILL.md` in the plugin. For entries that only exist as a slash command (`commands/<name>.md` with no `skills/<name>/SKILL.md` counterpart), the lookup fails — and the error message Claude Code uses is "Plugin not found" rather than the more accurate "Skill file not found".

Pre-v0.10.2:
- `skills/` had 15 subfolders → 15 entries load cleanly
- `commands/` had 31 files → the panel surfaced 31 entries
- 16 entries from `commands/` had no counterpart in `skills/` → 16 "Plugin not found" errors (and `obsidian-markdown` is the one skill with no command file, so 17 total mismatched if we count the inverse direction)

### Why not just file an upstream bug?

The wrong error message is a Claude Code UI bug worth reporting, but the deeper question is structural: the router has 30 slash commands, 18 MCP tools, and ~15 skills. The relationship between commands and skills was ad-hoc — some commands had rich descriptions and full bodies (like the old `commands/auto-mode.md` with 58 lines of mode-decision rules), some delegated to skills (`commands/autoresearch.md` is a 22-line dispatcher pointing to `skills/autoresearch/SKILL.md`).

The cleanest fix is to normalize: every `commands/<name>.md` is a thin dispatcher, every `skills/<name>/SKILL.md` is the source of truth. This is the pattern v0.8.3 established for 13 commands (skill-listing budget cleanup); v0.10.2 finishes the job for the remaining 17.

## What v0.10.2 does

### 17 new `skills/<name>/SKILL.md` files

Each new skill follows the established template:

```yaml
---
name: <name>
description: |
  <Long description with EN+FR natural-language triggers — preserved verbatim
   from the previous commands/<name>.md frontmatter>
---

# <name>

<Body: tool invocation, argument parsing, edge cases, anti-patterns, output format>
```

Grouped by surface:

| Surface | New skills |
|---|---|
| Router-state (3) | `auto-mode`, `lock`, `unlock` |
| Discovery (2) | `discover-list-files`, `discover-list-vaults` |
| Read (4) | `read-get`, `read-frontmatter`, `read-search`, `read-search-smart` |
| Write (5) | `write-append`, `write-create-or-replace`, `write-patch`, `write-frontmatter-set`, `write-frontmatter-merge` |
| Manage (2) | `manage-delete`, `manage-move` |
| Template (1) | `template-execute` |

The skills that carry non-trivial decision logic (and would benefit a reader who lands on them cold):

- **`auto-mode`** — when to pick `ClaudeAsk` / `Hybrid` / `FullAuto` / `off`, disambiguation of *"stop asking me"* (could mean three different modes), persist-mode inference from *"de manière permanente"*, homedir refusal caveat.
- **`lock`** — push-back when already locked to a different vault, persist-mode inference, homedir refusal caveat.
- **`manage-delete`** — the two-step confirm guard documented with explicit "first call previews + refuses, second call with `confirm=true` proceeds" protocol against hallucinated deletes in long sessions.
- **`template-execute`** — the `tp.mcpTools` vs `tp.user.mcpTools` footgun explained with WRONG/RIGHT code examples, plus the 503-when-Templater-missing handling.
- **`read-search-smart`** — pre-requisite check (the target vault must have both `obsidian-mcp-router-bridge` and `smart-connections` plugins installed and indexed), with explicit 503 handling.
- **`write-frontmatter-merge`** — non-atomicity warning (partial failures reported per-key), with an explicit alternative recipe for true atomicity (read + modify + `write-create-or-replace`).
- **`write-patch`** — the FULL-heading-path footgun (must be `Section::Sub`, not just `Sub`), common quick patterns, idempotency flag.

The trivial wrappers (`discover-list-vaults`, `read-get`, `read-frontmatter`, `write-append`, etc.) get a minimal SKILL.md anyway — enough for the panel to render and a curious reader to understand the parameters, but no padding.

### 17 `commands/<name>.md` files slimmed to dispatchers

Each command file is now 2–8 lines pointing to the matching skill. Example before/after:

**Before** (`commands/auto-mode.md`, 58 lines):
```markdown
---
description: |
  Set the wiki auto-enrichment mode for the current session — `ClaudeAsk` ...
---

Invoke the `set_auto_enrich_mode` MCP tool.

## Modes — when to pick which
...
## Argument parsing from $ARGUMENTS
...
[58 lines of content]
```

**After** (`commands/auto-mode.md`, 14 lines):
```markdown
---
description: Set the wiki auto-enrichment mode for the current session — `ClaudeAsk` / `Hybrid` / `FullAuto` / `off`. Pass "persist" to write the choice to the workspace `.env`. (Skill `auto-mode` handles natural-language triggers + mode decision rules.)
---

Invoke the `auto-mode` skill.

Required: the mode to switch to ...
The skill handles: ...
```

The skill is now the source of truth; the command file is the slash-command entry point + a 2-3 line description for the slash-command palette.

Pure plugin-content reorganization. Any user on v0.10.1 or earlier can upgrade to v0.10.2 with zero workflow change. Specifically:

- **Slash commands**: `/obsidian-router:auto-mode`, `/obsidian-router:lock`, `/obsidian-router:discover-list-files`, etc. all still work. The command file now delegates to the skill which holds the prior rich content.
- **Natural-language triggers**: *"liste les fichiers du dossier Sessions"*, *"verrouille sur tradingview de manière permanente"*, *"supprime Sessions/old-test.md"* (with confirm guard), etc. all still fire as before.
- **Configuration**: `~/.claude/obsidian-mcp-router/config.json` unchanged. `.env` env vars unchanged. `installed_plugins.json` entry unchanged (just the version bump on next `/plugin update`).
- **Multi-tenant env vars** (v0.9.0): `OBSIDIAN_ROUTER_ALLOWED_VAULTS`, `OBSIDIAN_ROUTER_READONLY`, `OBSIDIAN_ROUTER_USER_ID` all behave identically.

To pull v0.10.2:

```

```

## Why this matters

A plugin panel that surfaces 17 misleading "Plugin not found" errors creates two friction points:

1. **For new users** evaluating whether to install the router, the broken panel suggests a half-finished or buggy plugin.
2. **For existing users**, the error is a low-grade cognitive tax — every time they browse the Skills panel, they see red errors they have to mentally filter out as "not real".

The fix is structural rather than cosmetic: it normalizes the relationship between commands and skills, makes the source-of-truth location explicit, and surfaces the rich content where a curious reader expects to find it (in the skill body, not in a slash-command frontmatter that's rarely read).

This was also a discovery moment for the project's overall "version manifest hygiene" — the marketplace/plugin manifests had silently drifted 4 versions behind `package.json`. Going forward, the release checklist explicitly includes both files.
